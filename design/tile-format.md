# 타일 형식 명세 (MTIL v1) — 전국 스트리밍의 계약

상태: **설계 제안 + 스파이크로 검증됨.** 구현은 아직 없습니다.
스파이크 코드: [`tools/tile-spike`](../tools/tile-spike/README.md) · 브랜치 `spike/tile-format`

이 문서는 `WorldData` 한 덩어리를 받아 그리던 구조를, **PMTiles 아카이브 하나에서 필요한 조각만
Range로 받아 그리는** 구조로 바꾸기 위한 계약입니다. 여기서 정한 것 위에 엔진 스트리밍·타일 빌더·
호스팅이 얹힙니다.

이 문서에서 **"측정"이라고 쓴 숫자는 전부 실제로 재본 값**이고, 재보지 않은 것은 명시적으로
"미측정"이라고 적었습니다. §10에 미측정·미해결 목록을 모아 두었습니다.

## 1. 타일 분할 방식

### 1.1 격자: 슬리피 XYZ (웹 메르카토르)

우리 미터 격자가 아니라 표준 XYZ를 씁니다.

- PMTiles v3의 주소 체계 자체가 `(z, x, y)` → Hilbert 타일 id입니다. 우리 격자를 쓰려면 PMTiles의
  디렉터리를 버리고 별도 인덱스를 만들어야 하는데, 그러면 "타일 서버 불필요"라는 이점이 사라집니다.
- 임의 좌표에서 타일이 **결정적으로** 나옵니다. 상태가 전혀 필요 없습니다:

  ```js
  mx = (lng + 180) / 360
  my = 0.5 - ln((1 + sin φ) / (1 - sin φ)) / 4π
  x  = floor(mx · 2^z),  y = floor(my · 2^z)
  ```

  (구현: `tools/tile-spike/src/mercator.mjs`의 `tileOf`)

**기각한 대안 — 우리 미터 격자(예: 1 km 정사각형, EPSG:5179 기반).**
한국 한정이면 왜곡이 없고 타일이 정확히 정사각형이라 더 "깔끔"합니다. 그러나 (a) PMTiles 인덱스를
못 쓰고, (b) 나중에 한국 밖으로 나갈 때 격자를 갈아야 하며, (c) MapLibre·지도 툴체인 전체가 XYZ를
전제하므로 디버깅·검증 도구를 하나도 못 씁니다. 메르카토르의 위도별 스케일 왜곡(남한 위도에서
타일 한 변 970 m@z15, 북단과 남단 차이 약 6 %)은 타일 크기가 조금 달라지는 것뿐이고, 렌더링
좌표는 어차피 §2에서 미터로 환산하므로 문제가 되지 않습니다.

### 1.2 줌 레벨은 몇 개인가 — 측정으로

타일 하나의 gzip 크기를 실측한 뒤, 그 밀도로 **가득 찬 타일 하나**의 크기를 계산했습니다
(`node src/cli.mjs profiles`). 단위 KB, gzip 후:

| 지역 (밀도) | z11 | z12 | z13 | z14 | **z15** | z16 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 강남 (가장 조밀) | 4871 | 1329 | 361 | 98.7 | **28.5** | 8.1 |
| 부산 서면 | 3154 | 848 | 228 | 64.6 | **18.2** | 5.4 |
| 성수 | 3363 | 904 | 258 | 69.4 | **19.6** | 5.2 |
| 분당 (교외) | 1740 | 472 | 129 | 39.5 | **10.6** | 3.1 |
| 한강 (수면) | 991 | 277 | 75 | 20.2 | **6.5** | 2.1 |
| 김제 농지 | 1256 | 344 | 94.5 | 25.9 | **7.9** | 2.4 |
| 구례 (소도시) | 711 | 190 | 51.5 | 15.1 | **4.3** | 1.4 |
| 오대산 (산) | 0 | 0 | 0 | 0 | **0** | 0 |

**상세 레벨은 z15.** 타일 한 변 970 m(위도 37.5°), 면적 0.93 km².
가장 조밀한 강남에서도 **28.5 KB**, 보통 지역은 5~20 KB입니다. z14는 강남에서 100 KB에 육박해
근접 렌더링용으로는 한 번에 받기 부담스럽고, z16은 타일이 485 m라 카메라가 조금만 움직여도
요청 수가 4배로 늡니다. 요청 수 대 타일 크기의 균형점이 z15입니다.

**줌아웃 레벨은 별도로 필요합니다.** 같은 데이터를 z13에 담으면 강남 타일이 361 KB입니다.
저상세 프로파일(간선도로만, 높이 30 m 이상 또는 바닥면적 1500 m² 이상 건물만, 5000 m² 이상 공원,
POI 전부 제외)을 적용해 다시 측정하면:

| 지역 | z11 | z12 | **z13** |
| --- | ---: | ---: | ---: |
| 부산 서면 | 1511 | 407 | **110** |
| 강남 | 1401 | 377 | **102** |
| 성수 | 912 | 243 | **70** |
| 분당 | 800 | 216 | **59** |
| 구례 | 143 | 38.5 | **10.3** |

필터만으로 3~4배가 줄지만 z12는 여전히 240~400 KB라 못 씁니다. **측정으로 성립하는 줌아웃
레벨은 z13**(조밀 지역 ~110 KB, 타일 하나가 15 km² 커버)입니다.

> **미측정:** 기하 단순화(Douglas–Peucker를 줌 레벨별로 다시 적용)는 스파이크에서 하지 않았습니다.
> 단순화까지 넣으면 z12나 z11도 가능할 수 있지만, **재보지 않았으므로 가능하다고 쓰지 않습니다.**
> 줌아웃 품질이 중요해지면 이것이 다음 단계의 첫 작업입니다.

**결론: 아카이브 하나에 z13(overview)과 z15(detail) 두 레벨.** PMTiles는 한 아카이브에 여러 줌을
담을 수 있으므로 파일은 여전히 하나입니다. 어느 레벨을 쓸지는 카메라 거리로 엔진이 고릅니다
(중간 줌에서는 z15 타일을 축소해서 씁니다 — z14 하나를 z15 4장으로).

## 2. 좌표 원점 — 이게 가장 중요합니다

### 2.1 지금 전제가 깨지는 지점

`WorldData`는 `origin`(lng/lat) + `unitMeters`(보통 8) + `bounds`로 정의된 **로컬 접평면 하나**입니다.
전국이 되면 원점 하나로는 부산~서울 사이에서 좌표가 수십만 미터가 됩니다.

float32의 가수는 24비트이므로, 크기 *m* 근처에서 **표현 가능한 좌표 간격**은 `2^(⌊log2 m⌋ − 23)`입니다.

| 원점으로부터 거리 | float32 좌표 간격 |
| ---: | ---: |
| 1 km | 0.00006 m |
| 20 km | 0.001 m |
| 100 km | 0.008 m |
| 400 km (남한 대각선 규모) | **0.031 m** |

정점이 3 cm 격자에 스냅되면 건물 모서리가 떨리고, 모델·뷰·투영 행렬을 곱하면서 오차가 더 커집니다.
(깊이 버퍼의 z-파이팅이 실제로 언제 보이기 시작하는지는 **미측정**입니다 — 엔진에서 확인해야 합니다.)

### 2.2 결정: 타일 로컬 정수

타일 안의 좌표는 **그 타일 기준 정수**입니다. `extent = 8192`이면 타일 한 변이 0..8192으로
양자화되고, 여백(§3) 때문에 −256..8448 범위까지 나올 수 있어 부호가 필요합니다.

z15 · 위도 37.5°에서 한 칸 = **0.118 m**입니다.

측정한 왕복 오차 (`node src/cli.mjs verify`): 성수 샘플 건물 150동, 정점 전부 비교해서
**최대 0.0815 m**. 이론 상한(반대각선 0.118·√2/2 = 0.0837 m) 안입니다.
원본 `WorldData` 자체가 월드 단위 소수 2자리, 즉 0.08 m로 반올림되어 있으므로 사실상 원본 정밀도입니다.

`extent` 비용 (성수 z15, gzip 합계):

| extent | 격자 | gzip 바이트 | 변화 |
| ---: | ---: | ---: | ---: |
| 4096 | 0.237 m | 12,344 | −6.3 % |
| **8192** | **0.118 m** | **13,179** | 기준 |
| 16384 | 0.059 m | 14,044 | +6.6 % |

**8192를 씁니다.** 원본 반올림(0.08 m)과 비슷한 수준이고, 더 올려도 원본에 없는 정밀도를 사는
것뿐입니다. 6 cm가 필요해지면 +6.6 %에 살 수 있다는 것만 기록해 둡니다.

**기각한 대안 1 — 경위도 저장.** 도 단위 float64가 필요하고(float32 도 값은 위도에서 약 1 m 오차),
정점마다 16바이트가 됩니다. 델타 varint가 안 먹어서 gzip 후에도 훨씬 큽니다. 게다가 엔진이 정점마다
투영을 해야 합니다.

**기각한 대안 2 — 전역 웹 메르카토르 미터.** 값이 1.4×10⁷ 규모라 float32 간격이 **0.84 m**입니다.
근접 2.5D에서는 논외입니다.

### 2.3 엔진에 필요한 변경: rebase (이건 큰 변경입니다)

타일 로컬 좌표는 **엔진이 원점을 다시 잡을 수 있어야** 의미가 있습니다. 제안하는 구조:

1. 엔진이 **렌더 앵커(render anchor)** 하나를 float64 경위도로 들고 있습니다. 월드 좌표계는
   "앵커에서의 미터"입니다 (지금의 `origin` + `unitMeters`가 하던 역할).
2. 타일을 올릴 때, **타일 원점의 앵커 기준 오프셋**을 CPU에서 float64로 계산해 타일별 모델 행렬의
   평행이동에 넣습니다. 정점 자체는 타일 로컬 정수 → float32(최대 ±8448 · 0.118 m ≈ ±1 km)입니다.
   따라서 정점의 float32 오차는 **0.1 mm 수준**으로 고정되고, 거리와 무관합니다.
3. 카메라가 앵커에서 일정 거리 이상(**제안: 20 km**) 멀어지면 앵커를 카메라 아래로 옮기고
   **올라와 있는 모든 타일의 모델 행렬만 다시 계산**합니다. 정점 버퍼는 건드리지 않습니다.
   20 km에서 오프셋의 float32 간격은 0.001 m이므로 평행이동 정밀도도 충분합니다.
4. 앵커가 바뀌면 월드 좌표를 쓰는 **모든 것**(카메라 target, 캐릭터 위치, 지오펜스, 마커, 드롭,
   `project`/`unproject` 결과)이 같이 옮겨져야 합니다. 이게 진짜 비용입니다.

> **다음 단계가 각오해야 할 것:** 공개 API가 월드 단위 `{x, z}`를 주고받는 곳
> (`project`/`unproject`, `camera.center`, 캐릭터/마커/지오펜스 좌표)은 rebase 때 의미가 달라집니다.
> 앵커를 SDK 밖으로 노출하지 않으려면 **공개 API를 경위도 기준으로 바꾸고** 월드 단위는 내부 전용으로
> 내리는 편이 깔끔합니다. 이건 `@maprama/protocol`의 파괴적 변경이고, 이 브리프 범위 밖이라
> 여기서는 **필요하다는 사실만** 못 박아 둡니다.
>
> **미측정:** rebase 한 번에 드는 시간, 그리고 rebase 순간 화면이 튀지 않는지는 확인하지 않았습니다.

## 3. 경계에 걸친 피처

레이어를 두 부류로 나눕니다.

### 3.1 앵커 소유 — 건물, POI, 역, 지구 (자르지 않음)

- 건물은 **바닥면 앵커점**(면적 가중 중심, 퇴화한 링은 바운딩박스 중심)이 속한 타일 **하나**가 소유하고,
  기하는 **통째로** 들어갑니다. 타일 경계를 넘어가도 자르지 않습니다.
- 그래서: 건물에 **이음매가 절대 없고**, 같은 건물이 두 번 그려질 일도 없습니다. id 기반 중복 제거가
  아예 필요 없습니다. 건물이 2.5D에서 가장 눈에 띄는 요소라서 이 레이어에 가장 안전한 규칙을 씁니다.
- 대가: 타일 기하가 타일 경계 밖으로 삐져나갑니다. 실측한 최대 삐짐은 **45.9 m**(성수),
  27.1 m(분당)입니다. 원본에서 가장 큰 건물이 203 m이므로 상한은 그 절반 + 여유입니다.
  → **명세: 렌더러는 화면에 보이는 타일뿐 아니라 그 바깥 한 겹(최소 128 m)의 타일도 올려야**
  경계 근처 건물이 빠지지 않습니다. 컬링 계산에 이 여유를 반드시 넣으십시오.
- POI·역·지구는 점이므로 자를 것이 없습니다. 점이 속한 타일 하나가 소유합니다.
  POI의 `buildingId`가 **다른 타일의 건물**을 가리킬 수 있습니다(건물 앵커와 POI가 경계 반대편).
  엔진은 참조를 못 찾으면 조용히 무시해야 합니다 — 오류가 아닙니다.

**기각한 대안 — 건물도 클립.** 저장량은 조금 줄지만 잘린 벽면이 생기고, 인접 타일이 아직 안 왔을 때
건물이 반쪽만 서 있는 게 그대로 보입니다. 2.5D에서 이건 즉시 눈에 띄는 결함입니다.

### 3.2 클립 — 도로, 물, 공원

한강 하나, 경부고속도로 하나가 전국을 가로지르므로 통째 저장이 불가능합니다.

- 타일 + **여백 256 units**(z15에서 30 m)의 사각형으로 클립합니다.
  폴리라인은 Liang–Barsky, 폴리곤은 Sutherland–Hodgman.
- 도로가 여러 조각으로 잘리면 id에 `#0`, `#1` 접미사를 붙입니다. 원본 id는 `#` 앞부분이므로
  엔진이 같은 도로임을 알 수 있습니다.
- **이음매:** 클립 지점이 타일 경계에 정확히 일치하므로, 양쪽 타일이 올라와 있으면 기하가 정확히
  맞물립니다. 한쪽이 아직 없으면 그 자리에서 끊겨 보이는데, 이건 모든 타일 지도와 같은 성질입니다.
  여백 30 m는 도로 폭 절반과 선 끝 캡을 덮으므로 **경계에서 선이 가늘어지는 현상**을 막습니다.
- **⚠️ 물 가장자리 주의:** 엔진(`engine-web`)은 물 폴리곤에서 `banks`/`waterRibbons`를 파생합니다.
  클립으로 생긴 **타일 경계선 위의 변**에도 둑을 세우면 강 한가운데에 벽이 생깁니다.
  → **명세: 렌더러는 양 끝점이 모두 클립 사각형의 같은 변 위에 있는 변을 "합성 변"으로 보고
  둑·리본 파생에서 제외해야 합니다.** 클립 사각형은 타일이 아니라 **타일 + 여백**이므로 그 경계는
  `0`/`extent`가 아니라 **`-buffer`와 `extent + buffer`**(기본값으로 `-256`과 `8448`)입니다.
  별도 바이트는 쓰지 않습니다 — 기하학적으로 판별 가능하고, 진짜 벽이 클립 경계선과 정확히 일치할
  확률은 무시할 수 있으며, 오판의 대가는 둑 하나가 빠지는 것뿐입니다.

  > **정정 (2026-09-18, 파이프라인 구현 중 발견):** 이 문단은 원래 경계를 `0`/`extent`로 적었습니다.
  > **틀렸습니다.** 기하가 타일 + 여백으로 클립되므로 합성 변은 `-256`과 `8448`에 놓이고,
  > `0`/`extent`를 보는 렌더러는 **하나도 걸러내지 못한 채 강 한가운데에 벽을 세웁니다.**
  > 한강 반포(126.9971/37.5200) 주변 z15 타일 4장 실측: 클립 사각형 규칙 **12개 검출**,
  > `0`/`extent` 규칙 **0개 검출**. `@maprama/tiles`의 `isSyntheticEdge(a, b, extent, buffer)`가
  > 올바른 규칙이고, `maprama-tiles water` 명령으로 재확인할 수 있습니다.
  > (**여전히 미측정:** 이 규칙으로 실제 렌더링이 충분한지는 엔진 작업에서 확인해야 합니다.)
- 대가(중복 저장): 성수 z15에서 클립 조각 140개 / 통째 피처 484개. 줌이 올라갈수록 늘어나며
  (z17에서 195개), 이것이 §1.2 표에서 z16·z17의 KB/km²가 z15보다 큰 이유입니다.

## 4. 타일에 무엇을 담나

### 4.1 레이어

`WorldData`의 필드를 그대로 레이어로 옮깁니다. 레이어 id는 고정입니다.

| id | 레이어 | 소유 규칙 | 비고 |
| ---: | --- | --- | --- |
| 1 | `roads` | 클립 | `cls`, `bridge`, `name` |
| 2 | `buildings` | 앵커 | 높이는 **데시미터 정수**(월드 단위 아님), `levels`/`kind`/`name` |
| 3 | `water` | 클립 | |
| 4 | `parks` | 클립 | |
| 5 | `pois` | 앵커 | `buildingId`는 타일을 넘을 수 있음 |
| 6 | `stations` | 앵커 | |
| 7 | `districts` | 앵커 | |

빈 레이어는 아예 쓰지 않습니다. 모든 레이어가 비면 **타일 자체를 만들지 않습니다** — 오대산 샘플이
타일 0개인 이유이고, 전국 용량이 작게 나오는 가장 큰 이유입니다(§8).

### 4.2 `attribution` — 모든 타일에

표기 의무를 잃지 않으면서 타일당 바이트를 낭비하지 않는 절충:

- 아카이브 metadata(JSON)에 `attribution: ["© OpenStreetMap contributors", "건물 높이: …"]` 문자열 테이블.
- **모든 타일 헤더가 그 인덱스 배열을 직접 들고 있습니다.** 보통 `[0]` 또는 `[0,1]`이라 타일당 2~3바이트.
- 타일마다 출처가 다른 경우(국가 건물 데이터가 쓰인 타일 vs 아닌 타일)를 정확히 표현할 수 있습니다.
- 클라이언트는 타일을 읽기 전에 반드시 헤더+metadata를 읽으므로(§5의 3단계 흐름), 문자열을 모르는
  상태로 타일만 갖고 있는 경우는 생기지 않습니다.

문자열을 타일마다 통째로 넣는 방안도 검토했습니다. 40바이트 × 10만 타일 ≈ 4 MB로 치명적이진
않지만, 인덱스 방식이 같은 보장을 2바이트에 주므로 그쪽을 택했습니다.

### 4.3 월드 단위 필드는 어떻게 되나

| `WorldData` 필드 | 타일에서 |
| --- | --- |
| `origin`, `unitMeters`, `bounds` | **없음.** 타일 좌표계로 대체(§2). `unitMeters`는 엔진의 내부 표현일 뿐이고, 타일은 미터/데시미터로만 이야기합니다 |
| `plaza` | **없음.** 전국에는 "중앙 광장"이 없습니다. 광장은 이미 `cat: 'plaza'` POI로 들어 있으므로 데이터 손실은 없습니다. 카메라 초기 위치는 데이터가 아니라 **호스트 앱이 주는 설정**이어야 합니다 |
| `name` | 아카이브 metadata로 이동 |
| `version` | MTIL 헤더의 `version`, 그리고 metadata의 `format: "maprama-mtil-1"` |

### 4.4 페이로드 인코딩 (MTIL v1)

리틀엔디언. `varint` = LEB128, `svarint` = zigzag + varint.

```
magic    "MTIL"                       4 B
version  u8 = 1
flags    u8    bit0 = 클립됨
extent   u16
buffer   u16
attr     varint n, varint × n         metadata 문자열 테이블 인덱스
layers   varint n, layer × n
layer    u8 id, varint byteLength, bytes
```

`byteLength`가 앞에 있으므로 **모르는 레이어 id는 건너뜁니다** — 나중에 레이어를 추가해도 구형
클라이언트가 깨지지 않습니다. 기하는 MVT처럼 커서 델타(직전 정점 대비 zigzag varint, 피처의 첫
정점은 직전 피처의 마지막 정점 대비)입니다.

타일 전체를 gzip(레벨 9)해서 PMTiles에 넣습니다. 성수 z15 측정: 원본 21,450 B → gzip 13,179 B (−39 %).

**JSON 대비:** 같은 성수 데이터가 원본 JSON 124.8 KB/km², gzip JSON 31.2 KB/km², **MTIL gzip 20.9 KB/km²**.
JSON gzip 대비 1.5배, 원본 대비 6배 작습니다. 바이너리를 쓰는 이유가 이 1.5배이고, 그보다 중요한 건
**파싱 비용**(정수 델타 vs JSON.parse)이지만 **파싱 시간은 미측정**입니다.

## 5. PMTiles를 실제로 확인했습니다

### 5.1 우리 페이로드를 담아도 되는가 — 됩니다

PMTiles v3 스펙에는 타일 내용에 대한 제약이 없습니다. 헤더 99바이트의 `tile_type`이 열거형
(0 Unknown, 1 MVT, 2 PNG, 3 JPEG, 4 WebP, 5 AVIF)이고, **0 = Unknown이 "형식을 강제하지 않음"**입니다.
MVT가 아니어도 됩니다. 압축은 헤더 98바이트의 `tile_compression`(1 none, 2 gzip, 3 brotli, 4 zstd)로
선언하고 클라이언트가 그대로 풀어 줍니다.

우리 선택: `tile_type = 0`, `tile_compression = 2 (gzip)`, `internal_compression = 2 (gzip)`.

스파이크에서 **스펙만 보고 PMTiles v3 라이터를 직접 구현**하고
(`tools/tile-spike/src/pmtiles-write.mjs`, 헤더 127 B · 디렉터리 varint 델타 인코딩),
**공식 `pmtiles` 리더로 다시 읽어서** 검증했습니다. 바이트가 맞다는 것을 확인하는 유일하게 의미 있는
방법입니다. 결과:

```
header: specVersion=3  tileType=0(Unknown)  tileCompression=2  internalCompression=2
        minZoom=15 maxZoom=15 numAddressedTiles=4 clustered=true
        bounds=[127.0519998, 37.5410001, 127.0610002, 37.5479999]
metadata: {"format":"maprama-mtil-1","name":"Seongsu-dong, Seoul","extent":8192,
           "buffer":256,"attribution":["© OpenStreetMap contributors"],"layers":[...]}
```

### 5.2 Range로 조각만 받는 흐름

공식 리더(`FetchSource`)의 실제 동작을 서버 쪽에서 세어 확인했습니다:

1. `bytes=0-16383` — 헤더(127 B) + 루트 디렉터리 + metadata를 **한 번에** 가져옵니다.
2. (필요하면) 리프 디렉터리 한 조각.
3. 타일 하나당 range 요청 하나 (`tileDataOffset + entry.offset` ~ `+ length`).

즉 **콜드 스타트 3요청, 이후 타일당 1요청**입니다. 스파이크 검증 실행:
아카이브 13,527 B, HTTP 요청 4회, 전송 19,198 B(작은 아카이브라 첫 16 KB 요청이 파일 대부분을
가져오므로 전송량이 파일보다 큽니다 — 전국 아카이브에서는 16 KB 고정비입니다).

**전국 디렉터리 크기 (실측, 남한 bbox에 실제 z/x/y를 깔고 같은 인코더로 직렬화):**

| 줌 | 엔트리 | 단일 디렉터리(gzip) | 바이트/엔트리 | 2단 루트 | 리프 수 | 리프 평균 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| z14 | 17,656 | 32 KB | 1.86 B | 51 B | 5 | 10.0 KB |
| z15 | 70,397 | 54 KB | 0.79 B | 110 B | 18 | 11.0 KB |
| z16 | 280,736 | 142 KB | 0.52 B | 308 B | 71 | 11.2 KB |

z15 전국이면 루트가 110 B라 첫 16 KB 요청에 여유롭게 들어가고, 리프 하나가 11 KB입니다.
디렉터리는 용량·지연 어느 쪽에서도 문제가 아닙니다.

> **주의 (미구현):** 스파이크 라이터는 **루트 디렉터리만** 만듭니다(리프 없음). 전국 아카이브는
> 2단 구조가 필요합니다. 위 표의 2단 숫자는 같은 인코더로 실제 직렬화해 잰 것이지만,
> **라이터에 리프 생성이 들어가 있지는 않습니다.**

## 6. React Native에서 HTTP Range — 실측 결과

**가장 먼저 확인했고, 전부 통과했습니다.**

측정 방법: 로컬에 오리진 1개 + 서로 다른 CORS 설정의 "CDN" 2개를 띄우고
(`tools/tile-spike/src/range-probe-server.mjs`), Expo(RN 0.86 / react-native-webview 14) 프로브 앱을
**iOS 시뮬레이터(iPhone 17 Pro, iOS 26.5)와 Android 에뮬레이터**에서 실행해 결과를 서버로 회수했습니다.
WebView는 **Maprama가 실제로 쓰는 설정 그대로** `source={{ html }}`입니다.

| 항목 | iOS | Android |
| --- | --- | --- |
| RN JS `fetch` + `Range` + `arrayBuffer()` | ✅ 206, 바이트 일치 | ✅ |
| RN `XMLHttpRequest` `responseType='arraybuffer'` + Range | ✅ 206, 256 B | ✅ |
| WebView 문서 origin | `null` / `about:blank` | `null` / `about:blank` |
| WebView에서 교차 출처 Range (CORS 완비) | ✅ 206, `Content-Range` 보임 | ✅ |
| WebView에서 교차 출처 Range (ACAO만) | ✅ 206 — **단, `Content-Range`가 `null`** | ✅ 동일 |
| WebView에서 range로 받은 실제 MTIL 타일 gunzip | ✅ `DecompressionStream` 존재, magic `MTIL` | ✅ |
| Range 8개 동시 | ✅ 8/8 (39 ms) | ✅ 8/8 (28 ms) |
| RN JS 64 KB × 16 순차 | ✅ 1 MB / 51 ms | ✅ 1 MB / 218 ms |

여기서 나온 **설계에 영향을 주는 사실 세 가지**:

1. **`Range`는 CORS preflight를 유발하지 않습니다.** 서버 로그에 `OPTIONS` 요청이 한 번도 안 찍혔습니다.
   단순 바이트 범위 `Range`가 CORS-safelisted 요청 헤더가 되었기 때문입니다. CDN에 preflight 처리를
   따로 넣을 필요가 없습니다.
2. **엔진 WebView는 origin이 `null`입니다.** `source={{ html }}`이라 iOS·Android 모두 `about:blank`입니다.
   따라서 **같은 호스트에서 받아도 전부 교차 출처**이고, CDN은 반드시
   `Access-Control-Allow-Origin: *`를 보내야 합니다(자격 증명은 쓰지 않으므로 `*`로 충분).
3. **`Access-Control-Expose-Headers`가 없으면 `Content-Range`가 안 보입니다.** 그래도 본문은 옵니다.
   `pmtiles` 리더는 206 응답에서 `Content-Length`와 `ETag`를 읽고, 0번 오프셋 416 응답 처리에
   `Content-Range`를 씁니다. → **CDN 필수 헤더:**
   `Access-Control-Allow-Origin: *` / `Access-Control-Expose-Headers: Content-Range, Content-Length, ETag, Accept-Ranges` / `Accept-Ranges: bytes`.
   이게 빠지면 증상 없이 이상하게 동작합니다.

> **측정하지 않은 것:** 실기기(시뮬레이터/에뮬레이터만), 셀룰러 네트워크, 실제 CDN(CloudFront·Cloudflare R2 등),
> HTTP/2 다중화, 프록시/캡티브 포털이 Range를 깎는 경우, 그리고 `engine-native`(C++ / MapLibre Native)
> 쪽 네트워크 스택. 마지막 것은 별도 확인이 필요합니다.

## 7. `WorldSource`에 `kind: 'tiles'` 제안 (문서만 — 코드 변경 없음)

`@maprama/protocol`은 이 브랜치에서 건드리지 않았습니다. 모양만 제안합니다.

```ts
/** 전국 스트리밍: PMTiles 아카이브 하나에서 필요한 타일만 받는다. */
| {
    kind: 'tiles';
    /** PMTiles 아카이브 URL. Range 요청을 지원해야 한다. */
    url: string;
    /**
     * 처음 보여줄 위치. `kind: 'url'`과 달리 데이터가 원점을 정해 주지 않으므로
     * 호스트가 줘야 한다.
     */
    center: LngLat;
    /** 상세 레벨을 강제할 때. 기본값은 아카이브의 maxZoom. */
    detailZoom?: number;
    /** 줌아웃 레벨을 강제할 때. 기본값은 아카이브의 minZoom. */
    overviewZoom?: number;
    /** 한 번에 메모리에 둘 타일 수 상한. 기본값은 엔진이 정한다. */
    tileBudget?: number;
  }
```

아카이브 metadata(JSON) 계약:

```jsonc
{
  "format": "maprama-mtil-1",   // 필수. 클라이언트는 모르는 format이면 거부해야 한다
  "name": "South Korea",
  "extent": 8192,
  "buffer": 256,
  "attribution": ["© OpenStreetMap contributors", "건물 높이: …"],
  "layers": ["roads", "buildings", "water", "parks", "pois", "stations", "districts"],
  "profiles": { "13": "overview", "15": "detail" }
}
```

엔진이 새로 해야 하는 일 (전부 이 브리프 범위 밖):
타일 좌표 ↔ 월드 좌표 변환, 렌더 앵커와 rebase(§2.3), 타일 생명주기(로드/언로드/예산),
타일 경계 여백을 반영한 컬링(§3.1), 물 가장자리 합성 변 판별(§3.2),
그리고 `building:press`·`setBuildingStyle` 같은 **id 기반 API가 아직 안 올라온 타일의 건물을
가리킬 때** 어떻게 답할지에 대한 결정.

| 성수 | 0.615 | 428 | 101 | 124.8 | 31.2 | **20.9** |
| 부산 서면 | 1.087 | 554 | 423 | 119.2 | 27.8 | **18.4** |
| 분당 | 1.056 | 257 | 222 | 70.6 | 18.2 | **11.2** |
| 김제 농지 | 1.078 | 265 | 146 | 51.3 | 12.8 | **8.0** |
| 한강 | 1.054 | 64 | 157 | 34.1 | 9.4 | **6.9** |
| 구례 | 1.086 | 33 | 143 | 21.9 | 6.3 | **4.4** |
| 오대산 | 1.051 | 0 | 0 | 0.3 | 0.2 | **0.0** |

브리프의 "59 KB/km²"는 원본 JSON 기준의 수치로 보입니다. 우리 측정으로는 원본 JSON이
지역에 따라 22~208 KB/km²이고, **MTIL gzip은 0~30.5 KB/km²**입니다.

### 8.2 남한 100,000 km² 총량

| 시나리오 | KB/km² | **총 용량** | 비어있지 않은 z15 타일 | 평균 타일 |
| --- | ---: | ---: | ---: | ---: |
| **상한 (전 국토가 성수 밀도)** | 20.94 | **2.00 GB** | 107,066 | 19.6 KB |
| **보수적 혼합** | 6.68 | **0.64 GB** | 64,240 | 10.4 KB |
| **중간 혼합** | 4.49 | **0.43 GB** | 46,574 | 9.7 KB |
| 극단적 최악 (전 국토가 강남 밀도) | 30.5 | 2.91 GB | 107,066 | 28.5 KB |

z13 오버뷰 레벨을 더해도 (타일 면적이 16배라 타일 수는 1/16) **+0.03~0.15 GB** 수준입니다.

**답: 남한 전역 상세(z15) + 오버뷰(z13) 아카이브는 0.5~2.2 GB, 현실적으로는 1 GB 내외.**
타일 수는 z15에서 5만~11만, z13에서 3천~7천.

이 숫자가 작은 결정적인 이유는 **빈 타일을 아예 저장하지 않는 것**입니다. 남한은 국토의 60 % 이상이
산지이고, 오대산 샘플은 1 km²에 OSM 피처가 0개였습니다. 그런 타일은 PMTiles 디렉터리에 엔트리조차
생기지 않습니다.

**호스팅 관점:** 1~2 GB짜리 파일 하나면 오브젝트 스토리지(S3/R2) + CDN에 그냥 올려두면 됩니다.
타일 서버가 필요 없고, 스토리지 비용은 월 몇 센트 단위입니다. 비용은 전적으로 **전송량**에서 나옵니다
— 사용자 한 명이 한 세션에 z15 타일 수십~수백 장(수백 KB ~ 수 MB)을 받습니다.
(**미측정:** 실제 세션당 평균 타일 수는 엔진 스트리밍이 생겨야 잴 수 있습니다.)

### 8.3 생성 시간

측정한 것은 **`WorldData` → 타일 → PMTiles** 구간뿐입니다:
성수 0.615 km²가 타일링 8.4 ms + 아카이브 3.1 ms. km²당 3~11 ms.
전국 100,000 km²로 외삽하면 **단일 코어 1~6분**입니다.

> **정직하게:** 이 숫자는 파이프라인의 **마지막 구간만**입니다. 실제 전국 빌드의 비용은
> 한국 전체 OSM PBF(1 GB 남짓)를 읽어 `WorldData`를 만드는 앞 구간이 지배하는데,
> 그건 브리프 V(`tools/osm` PBF 입력)의 작업이고 **여기서 재지 않았습니다.**
> 국가 건물 데이터(GIS건물통합정보) 조인 비용도 미측정입니다.
> "타일화 자체는 몇 분이면 된다"까지만 말할 수 있고, "전국 빌드가 몇 분"이라고는 말할 수 없습니다.

## 9. 이미 있는 것과의 충돌 — `services/api`

이 저장소에는 **이미 PMTiles를 서빙하는 서비스가 있습니다.** 스파이크 중에 발견했고, 설계에 영향을 줍니다.

- `services/api`가 `pmtiles@4.5.0`(우리가 고정한 것과 **같은 버전**)을 쓰고, R2 바이트 범위 읽기로
  `tiles/<tileset>.pmtiles`를 읽습니다 (`src/tiles/pmtiles.ts`의 `BlobRangeSource`).
- `GET /v1/tiles/:tileset/:z/:x/:y.mvt`가 **API 키 인증 + 사용량 과금(`tile` 단위, 가중치 1)**을 거쳐
  타일 하나를 돌려줍니다. `GET /v1/tiles/:tileset.json`은 헤더+metadata로 TileJSON을 만듭니다.

여기서 두 가지가 걸립니다.

**(1) 지금 라우트는 우리 아카이브를 거부합니다.**
`src/routes/maps.ts`에 다음 줄이 있습니다.

```ts
if (header.tileType !== TileType.Mvt) throw new ApiError(404, 'NOT_FOUND', `Tileset "${tileset}" is not a vector tileset`);
```

우리는 `tile_type = 0 (Unknown)`을 쓰므로 **404가 납니다.** 경로도 `<y>.mvt`로 하드코딩되어 있습니다.
→ 서비스를 통해 내보내려면 `TileType.Unknown` 허용과 `.mtil` 같은 확장자 추가가 필요합니다.
작은 변경이지만 **이 브리프 범위 밖이라 건드리지 않았습니다.**
(`tileContentType`은 이미 `default: application/octet-stream`이라 그대로 맞습니다.)

**(2) "CDN에서 직접 Range"는 인증과 과금을 우회합니다.**
브리프의 전제("타일 서버 불필요, 오브젝트 스토리지 + CDN")는 대역폭과 운영 면에서는 옳지만,
아카이브 URL을 아는 사람은 **키 없이 전국 데이터를 통째로 받을 수 있습니다**(1~2 GB 파일 하나).
지금 서비스가 타일마다 과금하는 구조와 정면으로 다릅니다. 선택지는:

| 방식 | 대역폭·지연 | 인증/과금 | 비고 |
| --- | --- | --- | --- |
| A. CDN에서 직접 Range | 가장 좋음. 서버 0대 | **없음** | 서명 URL로 완화 가능하나 아카이브 전체 유출은 못 막음 |
| B. `services/api`가 z/x/y로 중계 (지금 구조) | 요청마다 워커 | 키 + 과금 | 위 (1) 변경 필요 |
| C. 둘 다 — 공개 티어는 A, 유료 티어는 B | | | |

**이건 기술 결정이 아니라 제품 결정이므로 여기서 정하지 않습니다.** 다만 타일 형식은 A·B 어느 쪽에도
그대로 쓰입니다(같은 아카이브, 같은 페이로드). 결정은 배포 방식에만 영향을 줍니다.

## 10. 이 설계로 안 되는 것 · 아직 모르는 것

**설계상 못 하는 것**

1. **타일 단위 갱신이 곧 전체 재배포입니다.** PMTiles는 오프셋 기반 단일 파일이라 타일 하나만
   교체할 수 없습니다. 지도 갱신은 아카이브 전체 재생성 + 재업로드(1~2 GB)입니다.
   주 단위/월 단위 갱신에는 맞고, 실시간 편집 반영에는 맞지 않습니다.
2. **폴리곤에 구멍이 없습니다.** `WorldData` 제약을 그대로 물려받습니다(안뜰, 강 속 섬).
3. **한 건물이 여러 타일에 걸쳐 나눠지지 않으므로**, 200 m가 넘는 거대 구조물은 타일 하나를
   국소적으로 키웁니다. 실측 최대 삐짐 45.9 m는 괜찮지만, 공항 터미널·대형 스타디움은
   **측정해 본 적 없습니다.**
4. **오프라인 저장은 이 설계가 답하지 않습니다.** Range 스트리밍 전제라, 지역 단위 오프라인
   다운로드를 하려면 아카이브 부분 복사본을 만드는 별도 장치가 필요합니다.
5. **`plaza`, `bounds`, `origin`이 사라집니다.** 이 필드에 의존하는 기존 앱 코드는 옮겨야 합니다.

**재보지 않은 것 (중요한 순서대로)**

1. `engine-native`(C++/MapLibre Native) 네트워크 스택에서의 Range — **iOS/Android의 JS·WebView만 확인했습니다.**
2. rebase의 실제 비용과 시각적 튐, z-파이팅이 실제로 나타나는 거리.
3. 기기에서의 MTIL 파싱 시간 (gzip 해제는 확인, 디코드는 미측정).
4. 줌아웃 레벨에 기하 단순화를 적용했을 때의 크기 (필터만으로는 z13이 한계).
5. 실제 CDN·실기기·셀룰러에서의 Range 동작.
6. 전국 PBF → `WorldData` 빌드 시간 (§8.3).
7. 물 가장자리 "합성 변" 규칙이 실제 렌더링에서 충분한지.
8. 공항 같은 초대형 건물의 타일 삐짐.
9. 세션당 평균 타일 수 = 전송 비용.

## 부록: 재현 방법

```sh
npm install
npm run build -w @maprama/protocol && npm run build -w @maprama/osm

cd tools/tile-spike
node src/cli.mjs build          # WorldData -> 타일 -> PMTiles 아카이브
node src/cli.mjs verify         # 공식 pmtiles 리더로 HTTP Range로 되읽기
node src/cli.mjs measure        # 지역별 밀도 표
node src/cli.mjs profiles       # detail vs overview 프로파일
node src/cli.mjs extrapolate    # 남한 전역 외삽
node src/cli.mjs directory      # 전국 PMTiles 디렉터리 크기
node src/range-probe-server.mjs # RN Range 프로브 서버 (§6)
```

성수 외의 지역 샘플은 `tools/tile-spike/scripts/fetch-areas.sh`로 Overpass에서 받습니다
(`.data/`, gitignore됨 — OSM 파생 데이터는 ODbL이라 저장소에 넣지 않습니다).
