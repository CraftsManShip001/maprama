# 타일 월드 (전국 스트리밍)

`WorldData` 한 덩어리는 도시 하나 크기까지입니다. 전국을 담으려면 지도를 **타일로 쪼개
CDN에 PMTiles 아카이브 하나로 올려두고, 카메라가 보는 조각만 HTTP Range로 받아야** 합니다.
그것이 `WorldSource`의 네 번째 종류인 `kind: 'tiles'`입니다.

형식은 [`design/tile-format.md`](https://github.com/CraftsManShip001/maprama/blob/main/design/tile-format.md)(MTIL v1)이고,
`@maprama/protocol`의 `decodeTile`이 그 명세의 리더, **`@maprama/tiles`가 아카이브를 만드는 도구**입니다
(`maprama-tiles build --pbf korea.osm.pbf --out korea.pmtiles`). 파이프라인이 쓴 바이트를 엔진이 그대로
읽는지는 `packages/engine-web/scripts/tile-interop.mjs`가 매번 확인합니다 — 저장소의 성수동 샘플을
파이프라인의 타일러·아카이브 라이터로 묶어 range 서버에 올리고 엔진으로 열어, 건물 좌표가
**0.05 m 안에서** 왕복하는 것까지 봅니다.

::: warning 지금 지원하는 엔진
`engine="web"`만 타일 월드를 그립니다. 네이티브 엔진(C++ 코어)은 명령과 **타일 페이로드 디코드**까지는
같은 코드로 처리하지만 스트리밍·렌더링이 아직 없어서, `init`에서 `error{unsupported, fatal: true}`로
분명히 거절합니다. 조용히 빈 지도를 보여주지 않습니다.
:::

## 쓰는 법

```tsx
<MapramaView
  engine="web"
  world={{
    kind: 'tiles',
    url: 'https://cdn.example.com/south-korea.pmtiles',
    center: { lng: 127.0565, lat: 37.5445 },   // 지도가 열리는 곳 (필수)
    // detailZoom: 15,      // 기본값: 아카이브의 maxZoom
    // overviewZoom: 13,    // 기본값: 아카이브의 minZoom
    // tileBudget: 96,      // 한 번에 메모리에 둘 타일 수 상한
  }}
  ui={{ attribution: true }}
/>
```

| 필드 | 뜻 |
| --- | --- |
| `url` | PMTiles 아카이브 주소. **Range 요청을 지원해야** 합니다 |
| `center` | 처음 보여줄 위치. `data`/`url` 월드와 달리 데이터가 원점을 정해 주지 않으므로 **호스트가 줘야** 합니다 |
| `detailZoom` | 근접 렌더링에 쓸 줌 레벨. 남한 아카이브는 z15(한 변 970 m) |
| `overviewZoom` | 줌아웃에 쓸 레벨. 남한 아카이브는 z13 |
| `tileBudget` | 메모리에 둘 타일 수 상한. 기본 96 |

## 호스팅: CDN이 반드시 보내야 하는 헤더

엔진은 인라인 HTML 문서(`source`에 `{ html }`을 주는 WebView) 안에서 돕니다. 그 문서의 origin은 iOS·Android 모두 **`null`**이라
**같은 호스트에서 받아도 전부 교차 출처**입니다. 다음이 없으면 증상 없이 이상하게 동작합니다.

```http
Accept-Ranges: bytes
Access-Control-Allow-Origin: *
Access-Control-Expose-Headers: Content-Range, Content-Length, ETag, Accept-Ranges
```

`Expose-Headers`가 빠지면 본문은 오지만 리더가 `Content-Range`를 못 읽습니다. 자격 증명은 쓰지
않으므로 `*`로 충분하고, 단순 바이트 범위 `Range`는 CORS preflight를 만들지 않으므로 `OPTIONS`
처리는 필요 없습니다. 아카이브를 열지 못하면 엔진이 이 헤더 목록을 그대로 담은
`error{world_load_failed}`를 보냅니다.

**아카이브 metadata(JSON) 계약:**

```jsonc
{
  "format": "maprama-mtil-1",   // 필수. 다른 값이면 엔진이 거부한다
  "name": "South Korea",
  "extent": 8192,
  "buffer": 256,
  "attribution": ["© OpenStreetMap contributors", "건물 높이: …"],
  "layers": ["roads", "buildings", "water", "parks", "pois", "stations", "districts"],
  "profiles": { "13": "overview", "15": "detail" }
}
```

## 요청은 얼마나 나가나

콜드 스타트에 **2~3 요청**(헤더 + 루트 디렉터리 + metadata를 첫 16 KB 한 번에), 그 뒤로 **타일당 1
요청**입니다. 아카이브가 1~2 GB라도 한 세션이 받는 것은 화면에 보이는 타일뿐입니다.

없는 타일은 **오류가 아닙니다.** 남한은 국토의 60 % 이상이 산지고 빈 타일은 아카이브에 아예
저장하지 않으므로, "타일 없음"은 **빈 바닥**을 뜻합니다. 엔진은 빈 답도 캐시해서 같은 구멍을
다시 묻지 않습니다. 타일 하나를 못 받으면 그 타일만 포기하고 `error{tile_load_failed, fatal: false}`를
한 번 보낸 뒤 지도는 계속 돕니다.

## 렌더 앵커와 좌표 재설정(rebase) — 이게 핵심입니다

### 왜 필요한가

렌더러가 굽는 정점 버퍼는 `Float32Array`입니다. float32는 크기 *m* 근처에서 `m · 2⁻²³` 간격밖에
표현하지 못하므로, 원점에서 400 km 떨어진 건물은 **3 cm 격자**에 스냅됩니다. 카메라가 움직일 때마다
건물 모서리가 떨리고 같은 높이의 면이 z-파이팅을 냅니다.

그래서 타일 월드는 **렌더 앵커**를 들고 다닙니다. 앵커는 월드 `{x: 0, z: 0}`의 경위도이고, 카메라가
앵커에서 **5 km** 이상 멀어지면 앵커가 카메라 위로 옮겨 오면서 월드의 모든 좌표가 같은 양만큼
평행이동합니다. 그러면 좌표 크기가 항상 8 km 안쪽이라 float32 격자가 **1 mm 미만**입니다.

> 5 km는 취향이 아니라 계산입니다. 적재된 타일 고리까지 합쳐 원점에서 약 8 km, `8000 / 2²³ ≈ 0.95 mm`.
> 명세가 제안한 20 km도 2.4 mm로 충분하지만, 임계값을 줄이는 비용은 "월드를 얼마나 자주 다시 조립하느냐"
> 뿐이고 월드는 어차피 타일이 바뀔 때마다 다시 조립됩니다. 실제로 rebase는 **가능하면 타일 변경과
> 같은 프레임에 묶여서** 재빌드를 한 번만 씁니다.

### 거리가 실제로 그림에 무슨 일을 하는가 — 측정

내용이 **바이트 단위로 같은** 블록을 같은 위도에 거리만 달리해 심어 두고, 앵커를 고정한 채 같은
경로로 날아가 같은 구도로 찍어 비교했습니다(`scripts/tile-shots.mjs --only precision`). 유일한 변수는
원점에서의 거리입니다.

| 앵커에서의 거리 | 기준 프레임과의 최대 채널 차이 | 다른 픽셀 |
| ---: | ---: | ---: |
| 대조군(같은 블록 재촬영) | **1 / 255** | 2 px |
| 8.2 km | 20 | 2.4 % |
| 15.9 km | 42 | 1.6 % |
| 31.4 km | 45 | 3.5 % |
| 124.5 km | 45 | 0.05 % |
| 434.8 km | 46 | 3.9 % |
| 931.3 km | **59** | 3.0 % |

차이는 **8 km 부근에서 나타나기 시작해** 곧 40~46 근처에서 포화하고, 931 km에서 59까지 갑니다.
전부 **경계 픽셀의 서브픽셀 커버리지**이고, 다른 픽셀 수가 들쭉날쭉한 것은 경계가 어디에 떨어지느냐에
달렸기 때문입니다.

**정직하게 덧붙이면:** 931 km 지점의 스크린샷과 기준 스크린샷을 나란히 놓고 봐도 **눈으로는 구분되지
않았습니다.** 엔진의 기본 카메라 거리 상한이 1,200 m라 931 km에서의 float32 격자(약 0.11 m)가 한 픽셀에
못 미치기 때문입니다. **z-파이팅은 어느 거리에서도 관찰되지 않았습니다** — 도로 표시와 횡단보도가 931 km
지점에서도 기준과 똑같이 그려졌습니다(깊이 정밀도는 월드 위치가 아니라 near/far 비율이 정하므로 예상된
결과입니다). 즉 engine-web에서 앵커의 근거는 "안 그러면 눈에 보인다"보다는 **숫자를 작게 유지해
측정 가능한 열화 자체를 없애고, 월드의 `bounds`·지면 평면·앞으로 올 float32 CPU 경로(engine-native)를
건전하게 두는 것**입니다.

### 왜 눈에 보이지 않는가

타일 월드의 좌표계는 **웹 메르카토르를 월드 기준 위도에서 실제 미터로 맞춘 것**입니다
(접평면 투영이 아닙니다 — 아래 참고). 그 배율은 월드가 살아 있는 동안 **절대 바뀌지 않으므로**
rebase는 **순수 평행이동**입니다. 카메라·지오메트리·캐릭터와 그 이동 경로·마커·정보 카드·지오펜스·
오버레이 앵커·라벨이 **같은 프레임 안에서 같은 delta**를 받습니다. 같은 양만큼 움직인 장면을 같은 양만큼
움직인 눈으로 보면 그림은 그대로입니다.

측정한 결과(`packages/engine-web/scripts/tile-shots.mjs`, 타일 구성과 카메라를 그대로 둔 채 앵커만 이동):

| 조건 | 전후 프레임 차이 |
| --- | --- |
| 그림자 끔 | 어떤 픽셀도 채널 차이 **2/255 이하**. 정점이 다른 float32 값에 놓이면서 생긴 경계 픽셀 커버리지 재양자화뿐 |
| 그림자 켬 | 최대 **30/255 내외**. 섀도맵이 월드 공간 텍셀 격자에 그려지므로 월드를 옮기면 그림자 경계가 재샘플링됩니다. 서브텍셀 팬이 만드는 것과 같은 현상입니다 |

두 경우 모두 **아무것도 움직이지 않습니다**. 비트 단위로 같지는 않고, 같을 수도 없습니다.

## 좌표계: 접평면이 아니라 메르카토르

`data`/`url` 월드는 `createProjection`의 **등거리 접평면**을 씁니다. 원점 위도의 코사인을 어디서나
쓰기 때문에 원점에서는 정확하고 멀어질수록 틀립니다.

```
오차 ≈ x · tan(lat₀) · Δlat  ≈ 1.2e-7 · D² m   (위도 37.5°, D = 동/북 거리)
```

2 km에서 0.5 m, 10 km에서 12 m, 20 km에서 48 m입니다. 이 투영으로 타일을 놓으면 **타일 경계마다 도로가
옆으로 어긋납니다.** 눈에 보이는 이음매이고 정밀도를 올려도 고쳐지지 않습니다.

그래서 타일 월드의 프레임은 웹 메르카토르입니다.

```
x = (mx − anchor.mx) · C · cos(refLat) / unitMeters
z = (my − anchor.my) · C · cos(refLat) / unitMeters
```

- **이음매가 원리적으로 없습니다.** 타일 로컬 정수 → 월드 단위 변환이 메르카토르 공간에서 선형이라
  타일 `x`가 끝나는 지점이 타일 `x+1`이 시작하는 지점입니다(차이는 float64 반올림 수준이고,
  `Float32Array`에 들어가면 **같은 숫자가 됩니다**).
- **rebase가 순수 평행이동입니다**(배율은 고정).
- **축척은 카메라 근처에서 정확하고 멀어지면 메르카토르처럼 조금씩 벌어집니다.** 다른 모든 웹 지도와
  같은 성질입니다. 한 월드 단위는 위도 φ에서 `unitMeters · cos φ / cos refLat` 미터이고, 남한 전역
  (위도 33 ~ 38.6)에서 그 폭은 **3.1 %**입니다. 엔진이 보고하는 미터 값은 **현재 앵커 위도 기준**이므로
  거리를 실제로 묻는 위치에서는 정확합니다.

## `data` 월드와 무엇이 같고 무엇이 다른가

`kind: 'data'`와 `kind: 'url'` 월드의 동작은 **한 글자도 바뀌지 않았습니다.** 아래는 타일 월드에서
의미가 달라지는 것만 모은 표입니다.

| API | `data` / `url` 월드 | 타일 월드 | 앱이 해야 할 일 |
| --- | --- | --- | --- |
| `project(coordinate)` → 화면 px | 같음 | **같음** | 없음 |
| `unproject(x, y)` → 경위도 | 같음 | **같음** | 없음 |
| `camera.center`, `camera:change`, `camera:idle` | 경위도 | **같음(경위도)** | 없음 |
| `setCamera({ center })`, `fitBounds`, `focusOn` | 경위도 | **같음** | 없음 |
| 캐릭터·마커·드롭·지오펜스·정보 카드 좌표 | 경위도 | **같음** | 없음 |
| `route`, `snapToRoad`, `snapToBuilding` | 경위도 + 미터 | **같음** (단, 적재된 타일 안에서만 탐색) | 화면 밖 먼 곳으로는 경로가 안 나올 수 있음 |
| 내부 월드 단위 `{x, z}` (`scene.toWorld` 등) | 세션 내내 고정 | **rebase 때 통째로 이동** | 월드 단위 좌표를 **저장하지 마십시오**. 경위도로 저장하세요 |
| `unitsToMeters` / `camera.distance`의 미터 | `unitMeters` 상수 | **앵커 위도 기준**, 전국에서 최대 3.1 % 변동 | 정밀한 측량 용도로 쓰지 마세요 |
| `world.plaza` | 있을 수 있음 | **없음**. `center`가 대신함 | `center`를 주세요 |
| `world.bounds` | 데이터 전체 범위 | **지금 적재된 타일의 범위**(계속 바뀜) | 의존하지 마세요 |
| `building:press` / `setBuildingStyle` | 모든 건물 | **적재된 타일의 건물만**. 모르는 id는 `unknown_building` | 화면 밖 건물 스타일은 다시 적재될 때 지정 |
| `labelsIndex` | 월드 로드 때 1회 | **타일이 바뀔 때마다 갱신** | 매번 갱신되는 목록으로 다루세요 |
| POI의 `buildingId` | 항상 같은 월드 안 | **다른 타일의 건물을 가리킬 수 있음** | 못 찾으면 조용히 무시(엔진도 그렇게 함) |
| 카메라 최대 거리 | 기본 1,200 m | 같음 — **오버뷰 레벨에 닿으려면 `maxDistanceMeters`를 올려야 함** | 전국 조망이 필요하면 `camera.maxDistanceMeters`를 키우세요 |

::: danger 월드 단위 좌표를 저장하지 마십시오
`scene.toWorld()`가 준 `{x, z}`는 **지금 앵커 기준**입니다. rebase가 일어나면 같은 땅이 다른 숫자가
됩니다. 앱이 위치를 보관해야 한다면 반드시 경위도로 보관하세요. 공개 API는 전부 경위도라서 이 문제를
만나지 않습니다 — `scene`(내부 API)을 직접 쓰는 경우만 해당됩니다.
:::

## 경계에 걸친 피처

형식이 레이어를 두 부류로 나눕니다([명세 §3](https://github.com/CraftsManShip001/maprama/blob/main/design/tile-format.md)).

- **앵커 소유 (건물·POI·역·지구)**: 바닥면 앵커가 속한 타일 **하나**가 기하를 통째로 가집니다. 잘리지
  않으므로 건물에 이음매가 없고 중복 제거도 필요 없습니다. 대신 기하가 타일 밖으로 삐져나옵니다
  (실측 최대 45.9 m). → 엔진은 **보이는 영역보다 128 m 넓게** 타일을 적재합니다. 그래야 앵커가 화면
  밖이고 벽만 화면 안인 건물이 사라지지 않습니다.
- **클립 (도로·물·공원)**: 타일 + 여백 256 units(z15에서 30 m)로 잘립니다. 여백이 겹치므로 경계에서
  도로가 가늘어지거나 선 끝 캡이 보이지 않습니다.

**물 가장자리 특별 규칙.** 엔진은 물 폴리곤에서 둑(rim)을 파생합니다. 클립으로 생긴 변에도 둑을 세우면
**강 한가운데에 초록 띠가 생깁니다.** 그래서 양 끝점이 모두 클립 사각형 위에 있는 변은 "합성 변"으로 보고
둑 파생에서 제외합니다. 순수 기하 판정이라 바이트를 쓰지 않고, 오판의 대가는 둑 1 m가 빠지는 것뿐입니다.

## 줌 레벨

상세(z15)와 오버뷰(z13) 두 레벨을 한 아카이브에 담고, 엔진이 **보이는 영역이 상세 레벨로 예산에
들어가는 동안은 상세**, 넘으면 오버뷰를 씁니다. 두 레벨을 섞지 않습니다 — 한 번에 한 세트, 한 월드,
해상도 사이 이음매 없음.

기본 카메라 거리 상한이 1,200 m라 **기본 설정으로는 오버뷰 레벨에 닿지 않습니다.** 전국 조망이
필요하면 `camera.maxDistanceMeters`를 올리세요(렌더러 상한은 월드 단위 1,000 = 기본 8 km).

## 성능과 메모리

- **정적일 때 유휴 프레임 0.** 네트워크 대기는 렌더 루프를 깨우지 않습니다. 타일 요청이 떠 있는 동안만
  `tiles` 렌더 소스를 잡고 끝나면 놓습니다. 측정: 안정된 타일 지도가 5초 동안 **0 프레임**.
- **타일 예산.** `tileBudget`(기본 96)을 넘으면 가장 오래 안 쓴 타일부터 버립니다. 그와 별개로 화면에서
  2타일 이상 멀어진 타일은 예산이 남아도 버립니다 — 300 km 밖 도시의 타일이 남아 있으면 월드 전체가
  전국 크기로 늘어나서 앵커를 둔 의미가 없어집니다.
- **알려진 약점: 타일이 바뀔 때마다 월드를 통째로 다시 조립합니다.** 그 프레임은 길어집니다. 이 저장소의
  합성 픽스처(185동)에서 헤드리스 소프트웨어 GL 기준 재조립 1회가 **약 1.3초**, 타일 경계를 넘으며
  패닝하면 240프레임 중 **7~9프레임**이 중앙값의 3배를 넘었습니다. 실제 GPU에서는 훨씬 짧지만
  **버벅임은 남습니다.** 개선 방향은 [로드맵](./architecture)에 적었습니다.
