# 2D ⇄ 2.5D 뷰 모드

Maprama는 기울어진 디오라마(2.5D)를 그리는 지도입니다. 하지만 같은 앱 안에서도 화면마다 필요한 게 다릅니다. 동네를 걸어 다니는 화면은 입체가 맞고, "내 주변 매장 40곳"을 한눈에 훑는 화면은 평면 지도가 맞습니다. 저사양 기기에서 "일단 가볍게"가 필요할 수도 있습니다.

`view`는 그 선택을 **앱에 넘깁니다**. 엔진은 절대 스스로 모드를 바꾸지 않습니다 — 줌 임계값도, 기기 등급도, `prefers-reduced-motion`도 모드를 바꾸지 않습니다(전환을 즉시 끝낼 뿐입니다).

```tsx
const [view, setView] = useState<ViewMode>('2.5d');

<MapramaView view={view} world={WORLD} theme={{ base: 'urban' }} />
<Button title="2D" onPress={() => setView('2d')} />
```

명령형도 있습니다. `ref.setView`는 **전환이 끝났을 때** resolve하므로, 전환 후에 측정하거나 캡처해야 하는 코드가 기다릴 수 있습니다.

```tsx
await map.current?.setView('2d', { durationMs: 400 });
// 여기서부터 지도는 정말로 평면입니다.
const { camera } = await map.current!.fitBounds(bounds, { padding: 24 });
```

두 방법은 섞어 써도 됩니다. 선언형 prop이 다음 렌더에서 이깁니다 — 다른 모든 prop과 같은 규칙입니다.

## "2D"가 무엇인지 먼저 정합니다

**피치를 0으로 내린 것은 2D가 아닙니다.** 위에서 내려다본 입체 건물은 오히려 더 이상해 보입니다 — 지붕만 보이는 상자 더미에 그림자가 길게 누워 있고, 건물 옆면은 원근 때문에 바깥쪽으로 퍼집니다. 그래서 2D 모드는 렌더러가 다음을 **모두** 바꿉니다.

| 바뀌는 것 | 어떻게 | 왜 |
| --- | --- | --- |
| 건물 | 돌출을 버리고 **바닥 폴리곤 채움 + 외곽선**으로 그립니다 | 높이를 0으로 눌러도 지붕 자재·난간·파사드 텍스처·접지 그림자 데칼이 전부 지면에 겹쳐 z-파이팅을 냅니다. 지도가 건물을 그리는 방식은 "채움 + 외곽선"입니다 |
| 그림자 | 끕니다(그림자 패스 자체가 사라집니다) | 그림자는 높이를 읽게 하는 장치인데 2D에는 높이가 없습니다 |
| 피치 | 0으로 고정하고 **제스처까지 잠급니다** | 2D라고 해 놓고 손가락으로 기울어지면 모드가 거짓말이 됩니다 |
| 거리 안개(fog) | 끕니다 | 피치 0에서는 화면의 모든 지면이 대체로 같은 거리라, 안개가 깊이가 아니라 **화면 전체에 깔린 뿌연 막**이 됩니다 |
| 하늘 헤이즈·비네트·시네마틱 그레이딩·광선 | 함께 사라집니다 | 같은 이유입니다. 전부 "카메라와 장면 사이의 공기"를 표현하는 장치입니다 |
| 거리 소품(가로등, 벤치, 주차 차량, 버스 정류장) | 숨깁니다 | 바로 위에서 보면 알아볼 수 없는 작은 덩어리인데, 정적 월드에서 가장 조밀한 부분입니다 |
| 앵커 높이 (홀로 라벨 줄기, 드롭 아이템의 부유, 지붕 위 정보 카드) | 지면으로 내립니다 | 아래 참고 |

### 앵커 높이는 장식이 아니라 정확도 문제입니다

원근 카메라는 바로 위에서 내려다봐도 **높이 `h`에 있는 점을 그 아래 지면 점보다 화면 중심에서 더 바깥에** 투영합니다. 즉 2D에서 높이를 그대로 두면 핀이 자기 좌표 **옆에** 찍힙니다. 그래서 2D에서는 떠 있는 앵커가 전부 지면으로 내려옵니다.

지붕에 붙은 정보 카드(`anchor: 'roof'`)는 별도 처리가 필요 없습니다. 카드의 기준 높이는 매 프레임 건물에서 다시 읽는데, 2D는 이미 그 건물을 지면까지 내려놓았기 때문입니다.

## 전환은 기본이 애니메이션입니다

건물이 순간이동하듯 솟거나 꺼지면 싸구려로 보입니다. `setView`는 `animate`를 주지 않으면 **애니메이션이 기본**이고(`VIEW_TRANSITION_MS`, 450 ms), 건물 높이와 피치를 함께 보간합니다.

```tsx
map.current?.setView('2d');                          // 450 ms 애니메이션
map.current?.setView('2d', { durationMs: 250 });     // 더 짧게
map.current?.setView('2d', { animate: false });      // 즉시
```

- **전환 중 다시 `setView`** 를 보내면 **지금 상태에서 되돌아갑니다**. 처음부터 다시 시작하지 않으므로 토글을 두 번 누르면 한 번의 연속된 움직임으로 보입니다. 남은 거리에 비례해 시간도 줄어듭니다.
- **전환 중 다른 명령**은 그대로 처리됩니다. 전환이 소유하는 것은 **피치뿐**입니다. `setCamera`·`fitBounds`·`focusOn`·제스처는 그동안에도 중심·거리·베어링을 계속 움직입니다.
- `prefers-reduced-motion`이 켜져 있으면 전환은 즉시 끝납니다(모드 자체는 바뀌지 않습니다).

전환 시작과 끝은 `view:change` 이벤트로 나갑니다.

```tsx
map.current?.addEventListener('view:change', (e) => {
  // e.view는 "가고 있는 모드", e.animating은 "아직 움직이는 중인가"
  setChromeFor(e.view);
});
```

## 2D에서 `setCamera`에 피치를 주면 — **거부합니다**

세 선택지가 있었습니다: 거부, 무시, 모드 자동 해제. Maprama는 **거부하고 알립니다**.

- 조용히 무시하는 것은 하지 않습니다. 앱이 지도가 자기 말을 들었다고 믿게 됩니다.
- 모드를 자동으로 해제하지도 않습니다. 선언형 `view="2d"` prop과 싸우게 됩니다 — 다음 렌더에서 앱이 다시 2D로 돌려놓고, 무한 왕복이 됩니다. 그리고 앱이 **명시적으로 정한 모드**가, 카메라 이동에 딸려 온 피치보다 우선입니다.
- 명령 전체를 실패시키지도 않습니다. `setCamera({ center, pitch })`로 저장해 둔 카메라를 복원하는 건 흔한 패턴인데, 중심까지 버리면 더 놀랍습니다.

그래서: **피치만 0으로 고정되고, 같은 명령의 나머지(중심·거리·베어링·`follow`)는 전부 적용되며, 한 번의 비치명적 `error` 이벤트가 나갑니다.**

```
code: "view_pitch_locked"
message: pitch 45° was ignored: the "2d" view keeps the pitch at 0°.
         Send setView("2.5d") first (the rest of the command was applied).
```

같은 값으로 반복해서 보내도 경고는 한 번만 나갑니다(`camera_limits_clamped`와 같은 규칙).

`fitBounds`와 `focusOn`의 `pitch`도 똑같이 처리됩니다. 다만 여기서는 **솔버에 들어가기 전에** 잘립니다 — 적용되지도 않을 피치로 상자를 맞춰 놓고 그 카메라를 결과로 돌려주면 거짓말이 되기 때문입니다. 덤으로 피치 0에서는 보이는 지면이 사다리꼴이 아니라 직사각형이라 `fitBounds`가 훨씬 단순·정확해집니다.

제스처도 같습니다. 2D에서 두 손가락 드래그는 **회전과 핀치 줌은 그대로 동작하고 기울이기만 하지 않습니다**. 나침반(정북) 버튼도 2D에서는 방향만 북쪽으로 돌리고 지도를 세우지 않습니다.

## 성능: 2D는 확실히 더 쌉니다

이건 부수 효과가 아니라 목표입니다. 저사양 기기용 도피처로 쓸 수 있어야 합니다.

`packages/engine-web/scripts/view-cost.mjs`가 같은 카메라에서 두 모드를 번갈아 재고, 드로우 콜·삼각형 수(정확한 값)와 패닝 중 fps(같은 호스트에서의 상대값)를 보고합니다. 2026-09-17, headless Chrome(SwiftShader) / 390×760 / `realistic` 테마, 3회 중앙값:

| 월드 | 모드 | 드로우 콜/프레임 | 삼각형/프레임 | 패닝 fps | 정적 유휴 프레임 |
| --- | --- | ---: | ---: | ---: | ---: |
| 절차적 town (건물 208) | 2.5D | 846 | 213,773 | 9.1 | 30 |
| 절차적 town (건물 208) | **2D** | **42** | **127,034** | **13.5** | **0** |
| 성수 OSM 샘플 (건물 428) | 2.5D | 2,950 | 157,574 | 5.9 | 0 |
| 성수 OSM 샘플 (건물 428) | **2D** | **29** | **107,186** | **17.4** | **0** |

- **드로우 콜 20~100배 감소.** 2.5D는 건물 하나가 벽·상가 띠·지붕·난간·트림·장식으로 여러 드로우 콜이고, 그림자 깊이 패스가 그걸 한 번 더 그립니다. 2D는 모든 바닥 폴리곤을 **색상별 병합 메시 1개 + 외곽선 메시 1개**로 합칩니다 — 도시 전체가 보통 7개 안팎입니다.
- **삼각형 1.5~1.7배 감소**, 그리고 남은 삼각형은 전부 지면에 누운 언릿(unlit) 폴리곤이라 오버드로와 픽셀 셰이딩 비용이 훨씬 낮습니다. 소프트웨어 GL에서 fps가 1.5~2.9배로 오른 이유가 이것입니다.
- **정적일 때 유휴 프레임 0**은 그대로입니다. 전환 중에만 활성 렌더 소스를 잡고 착지하는 프레임에 놓습니다. 절차적 town의 2.5D가 30프레임인 것은 그 월드의 랜드마크 첨탑이 계속 회전하기 때문인데, 2D에서는 그 건물이 아예 그려지지 않으므로 회전도 멈춥니다.

`node packages/engine-web/scripts/idle-frames.mjs`에도 2D 구성이 들어 있습니다. 라벨을 켜든 끄든, 정보 카드를 5장 띄우든 2D 정적 지도는 **0 프레임**입니다.

## 네이티브 엔진에서는

`engine="native"`(MapLibre Native)는 아직 **프로토콜만** 구현돼 있습니다. C++ 코어가 `setView`와 `init.view`를 디코드·검증한 뒤 경고 로그를 남기고 무시합니다(`packages/engine-native/DESIGN.md`의 명령 표). 네이티브 평면 뷰는 남은 작업입니다. 지금 2D가 필요하면 기본값인 웹 엔진을 쓰세요.

## 이름에 대해

속성 이름은 `view`, 값은 `'2.5d' | '2d'`입니다. `flat`도 후보였지만 값 하나만 이름이 붙고 반대쪽("diorama"?)은 어색해집니다. 사용자가 이 기능을 부르는 말이 그대로 "2D ↔ 2.5D 전환"이기도 하고, 라이브러리 자체가 "2.5D 게임 지도"로 설명되므로 값이 곧 설명이 되는 쪽을 골랐습니다.

`theme.zoomOut`(카메라가 멀어질 때의 동작)과는 **별개의 축**입니다. 저쪽은 카메라 거리가 몰고 가고, 이쪽은 앱이 정합니다. 둘은 동시에 켜져 있어도 됩니다.
